# Plan: Introduce LazyBrain on the Lazy Coding Agent website

## Goal
Explain LazyBrain as a related but distinct project on the Lazy Coding Agent home page, link to its live site, and give LazyBrain a dedicated overview page on this site. Maintain the existing static-site conventions and clearly distinguish LazyBrain from the desktop application's planned “The Brain” feature.

## Facts reviewed
- `https://brain.lazycodingagent.com/` describes LazyBrain as a shared knowledge base/team memory for people and AI agents. MCP-capable clients can search and update project knowledge; the landing page names Cursor, Claude, ChatGPT and other assistants.
- Its listed capabilities include organization-level shared brains and roles, documents and memories, attributed search results distinguishing verified memories from proposals, knowledge history and optional review, folders/links/file storage, and client connections (Cursor bearer token; ChatGPT, Claude and Gemini OAuth, revocable).
- LazyBrain is in beta and free during the beta. Its own site explicitly warns users not to store PII, secrets, credentials or other sensitive information during beta.
- The current Lazy Coding Agent site is framework-free static HTML/CSS. Its home is `index.html`; `roadmap.html` currently describes “The Brain” as an application future-feature placeholder with no backend. `tools/check_site.py` validates page inventory, canonical URLs, internal links, accessibility basics and the sitemap.

## Proposed work

### 1. Add a home-page introduction
Update `index.html` with a visually consistent section/card after the desktop workspace feature sections and before the maturity/download notice. Introduce LazyBrain as a related project, describe its shared team memory and MCP-based connection to multiple assistants, and make the distinction explicit: LazyBrain is a separate web service, not a feature/backend currently integrated into the Lazy Coding Agent desktop application. Include a primary link to the dedicated local overview page and a direct external link to `https://brain.lazycodingagent.com/` (open in a new tab with safe `rel` attributes if using `target`).

### 2. Create a dedicated overview page
Add root-level `lazybrain.html` using the site's existing page template and styling:
- Unique title, description, canonical URL (`https://lazycodingagent.com/lazybrain.html`), Open Graph metadata, one descriptive H1, skip link, main landmark, site header/footer, and responsive navigation consistent with the other root pages.
- Explain the problem it addresses (project knowledge is not shared across separate assistant/vendor sessions), how the shared brain and MCP clients work, and the distinction from Lazy Coding Agent's desktop product.
- Summarize the publicly listed capabilities without implying unlisted behavior or guaranteed availability.
- Label beta status and free-beta access as current statements from LazyBrain's public page; include a prominent safety notice advising against sensitive data, secrets and credentials during beta.
- Link out to the LazyBrain landing page for current details and beta signup; let that external site own account actions and current terms.
- Link back to Lazy Coding Agent (home/features) and the related-project home section.

### 3. Clarify the existing roadmap item
In `roadmap.html`, revise the “The Brain” placeholder so it is clear that it refers to a previously proposed in-app adaptive memory capability, and is not the same as the separate LazyBrain service. Link the card to `lazybrain.html` for the separate related project, while retaining the status qualification that the desktop application's placeholder has no documented backend. This prevents the current roadmap entry from contradicting the newly introduced live service.

### 4. Register the page with site integrity and discovery
- Add `lazybrain.html` to `tools/check_site.py`'s `PAGES` list and `EXPECTED_CANONICALS` map so it receives the same static validation as other pages.
- Add its canonical URL to `sitemap.xml`.
- No `robots.txt` change is indicated; the site currently has a sitemap and the new page is an ordinary indexable page.

## Content and wording guardrails
- Treat the public LazyBrain page as the source for the described service. Keep claims close to the facts listed above and avoid unsupported security, privacy, uptime, pricing-after-beta, or integration claims.
- Keep the sensitive-data warning visible on both the dedicated overview and home-page introduction or ensure the home-page link makes the warning immediately apparent; the dedicated overview must state it clearly.
- Do not imply that LazyBrain implements the desktop app's planned RAG/Brain feature, that the desktop client currently integrates with LazyBrain, or that the services share accounts/data.
- Preserve the existing static, no-framework architecture, document-relative local links, native semantic navigation, focus/reduced-motion behavior and accessible heading structure.

## Validation
1. Run the site's existing `tools/check_site.py` integrity checker after implementation; add/fix any page registry or link failures it identifies.
2. Review the rendered home and `lazybrain.html` at desktop and narrow/mobile widths for section hierarchy, call-to-action prominence, wrapping, and navigation consistency.
3. Confirm the dedicated page has exactly one H1, working local and external links, correct canonical/OG URLs, and a clear beta sensitive-data warning.
4. Confirm the roadmap copy still marks the in-app feature as planned and differentiates it from LazyBrain.
5. Check that `sitemap.xml` parses and includes the new canonical URL.

## Files expected to change
- `index.html`
- `lazybrain.html` (new)
- `roadmap.html`
- `sitemap.xml`
- `tools/check_site.py`

No application code or LazyBrain service code will be changed.
