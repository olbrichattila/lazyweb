# Refresh the download-page release fallback to v0.1.27

## Finding and scope

As of this review, GitHub's public `releases/latest` API reports **v0.1.27**, published 2026-10-26 at 21:49:38 UTC, with `draft: false` and `prerelease: false`. The checked-in download page still has a v0.1.23 fallback and its status note dates that metadata to 2026-10-25. The optional updater already fetches GitHub's latest release at runtime and can refresh version, asset links, filenames and valid SHA-256 digests; the present task is to bring the no-JavaScript/API-failure fallback and its factual documentation in line with the currently observed release.

The public API response contains six matching platform assets: Windows setup, macOS Intel and Apple Silicon DMGs, Linux amd64 and arm64 DEBs, and x86_64 AppImage. GitHub supplied SHA-256 digests for all six. This plan is limited to static-site release metadata and documentation; it does not assert that the products have been independently installed or that the site has been deployed/tested.

## Files to update

1. **`download.html`** — update all checked-in fallback data as one coherent set:
   - Change version references in title and description/Open Graph metadata, visible version, status text, release tag link, filenames, direct asset URLs, checksum heading, checksum explanation, and fallback checksum rows from v0.1.23 to v0.1.27.
   - Use each exact asset filename, browser download URL and GitHub `digest` value from the current release API response. Keep the existing platform identifiers and artifact mappings intact.
   - Replace the old dated fallback-verification status with a precise statement that the fallback metadata/digests were checked against GitHub Releases on 2026-10-26; retain the caveat that these are API-published digests, not independently downloaded-and-hashed files.
   - Ensure every version-bearing text/metadata field and all six links, names, and digest rows agree on v0.1.27. Preserve the GitHub releases index CTA and existing install/maturity caveats.

2. **`README.md`** — refresh the Downloads section to describe the checked-in v0.1.27 fallback, current verification date, release tag/page/API source, publication state and timestamp, asset names/URLs/digests, and the existing caveat that no files were independently hashed. Update the publishing guidance only if necessary; retain its policy to recheck the API, update fallback data together, and test both success and failure behavior before making verification claims.

3. **`docs/PRODUCT_FEATURE_INVENTORY.md`** — update the downloads evidence row and verification gate so v0.1.23 is no longer represented as the current fallback. Record that v0.1.27 was observed as latest in the 2026-10-26 API check, and preserve explicit limits for asset hashing, runtime/install, browser and deployment verification.

4. **`docs/WEBSITE_CONTENT_PLAN.md`** — refresh the evidence boundary and download-page content/qualification entries from v0.1.23 and the 2026-10-25 snapshot to the v0.1.27 check on 2026-10-26. Preserve all existing maturity, browser-test, installation and deployment caveats.

5. **`tools/test_latest_release.js`** — update the test fixture's `fallbackVersion` to `0.1.27` and adjust fallback URL/version assertions accordingly. Keep the test's purpose and behavior unchanged: success refreshes, failed/stalled/malformed API leaves current fallback intact, digest-less and absent assets are treated safely, and malformed checksum markup does not interrupt other assets.

6. **`tools/check_site.py`** — inspect its release-fallback assertions before editing. If it hardcodes v0.1.23, update that test expectation to v0.1.27; do not weaken any integrity checks. The inspected constants currently map artifact suffixes rather than a specific version, but verify the rest of the file first.
