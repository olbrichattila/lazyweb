# Add a prominent GitHub Releases download button

## Goal
Add a clearly styled **Download** button at the top-right of the site header. It should link directly to `https://github.com/olbrichattila/lazycodingagent/releases` and open in a new browser tab. Preserve the existing in-site Download navigation link, which leads to the release-status information page.

## Repository synchronization and current state
- The inspected working tree is clean (`git status` reported no local changes).
- The available project tools are read-only for Git and this session is in Plan mode, so a remote fetch/pull could not be performed and incoming remote changes could not be checked. Do not claim the branch is up to date. Before implementing, check the remote/tracking state and pull applicable updates first, then re-check for conflicts or local changes before editing.

## Findings
- This is a static HTML/CSS website; there is no build system or shared templating layer.
- The current header has a brand, desktop navigation and a native `<details>` mobile menu. Each has an internal `Download` link to `download.html`; it does not link to GitHub Releases.
- The shared header is repeated in `index.html`, `features.html`, `agents.html`, `download.html`, `roadmap.html`, `community.html`, `privacy.html`, `blog/index.html`, and `docs/index.html`. `404.html` has a reduced header containing only the brand.
- `assets/site.css` provides reusable `.button` styling. The header uses a flex layout; at widths below 800px desktop navigation is replaced by the mobile menu.
- `download.html` explicitly says no release link is offered and that the release destination/assets have not been inspected. The homepage similarly says the site does not offer a download. Those statements would become inaccurate once the requested releases link is added, even though actual release availability remains unverified.
- `README.md` currently says not to add download links until the canonical release destination is confirmed. The user has now provided the intended URL, but the release page/assets and current availability have not been externally verified.

## Proposed implementation
1. After synchronizing the branch, add a prominent external `Download` anchor to the shared header pattern on the regular site pages. Position it at the far right after the desktop navigation, retaining the existing internal `Download` menu item so visitors can still reach the site's release-status/developer-information page.
2. Use the exact owner-provided releases URL and `target="_blank"`. Add `rel="noopener noreferrer"` for safe new-tab behavior. Keep the visible link text concise and accessible (for example, `Download`) and apply the existing `.button` visual treatment through a dedicated header modifier class so it remains visually distinct from normal navigation links.
3. Ensure the button remains available at narrow widths alongside the mobile menu; adjust header spacing/CTA sizing if needed so the brand, menu control, and CTA fit at 320px without overflow. Preserve keyboard focus visibility, adequate tap size, and existing navigation accessibility.
4. Apply the consistent CTA to all pages with the full site header, including nested `blog/` and `docs/` pages (the destination is absolute, so no relative-path variation is needed). Decide whether to add it to the simplified 404 header as well; favor a small right-aligned CTA there for consistent access without adding the full navigation.
5. Revise availability language in `index.html`, `download.html`, and `README.md` as needed: clearly distinguish that a direct link to the GitHub Releases page is provided from any claim that a release/package is published, available, tested, or ready to install. Do not add version numbers, asset names, checksums, installation instructions, or readiness claims without verification. On `download.html`, make the user-provided destination clickable while preserving its release-pending caveats.
