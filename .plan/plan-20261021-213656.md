## Findings and recommended work

### P1 — Correct outdated canonical release evidence and editing instructions

**Observed:** `docs/PRODUCT_FEATURE_INVENTORY.md` still says v0.1.12 was verified, calls for manual version/URL updates, and describes v0.1.12 as current. `docs/WEBSITE_CONTENT_PLAN.md` repeats the v0.1.12 status and prescribes direct v0.1.12 links/manual bumping. `README.md` describes the latest API-based approach, but its editing section says no script is needed and the download section contains redundant blank space/manual fallback instructions.

**Update:** Revise these documents to distinguish (a) the automatic browser-time lookup of GitHub's latest published release, (b) the checked-in v0.1.15 fallback and its digests, and (c) what has or has not been externally verified. Replace obsolete manual-only instructions with a release-maintenance procedure: confirm expected assets and digest availability, update fallback values when publishing, and verify the deployed page/API behavior. Remove contradictory or redundant instructions.

**Acceptance:** A repository-wide search finds no v0.1.12 claim presented as current and no assertion that download version/links always require manual updates. Documentation explicitly identifies the fallback and makes no unsupported claim that the API or deployment was live-tested.

### P1 — Make the release refresh script robust against incomplete asset metadata

**Observed:** `assets/latest-release.js` checks only that a checksum row contains at least one `<code>` element, then unconditionally writes `codes[1].textContent`. If markup changes or an expected asset is incomplete, this can throw and stop processing the remaining checksums. Asset matching assumes six exact filename suffixes; missing assets hide matching download links/checksum rows, but the page does not explain why a platform is unavailable. API fetch has no timeout, and the checked-in fallback is the only protection when the request fails.

**Update:** Guard each checksum row's required elements; isolate malformed/missing data so one asset cannot abort updates for others. Define explicit behavior for incomplete release assets (keep usable fallback links or clearly indicate unavailable platforms; never leave a misleading active download). Add a bounded request timeout and keep failure handling non-destructive. Ensure the release title, fallback content and fetched data cannot become internally inconsistent after partial updates. Keep asset discovery based on the known supported artifact names unless the application release naming contract is verified.

**Acceptance:** Simulated successful, failed, timed-out, malformed, digest-less, and partially populated release responses do not cause uncaught errors or corrupt the fallback page. Missing downloads are communicated accessibly and checksums are displayed only when valid. Existing no-JavaScript/API-failure fallback remains usable.

### P1 — Update privacy and site documentation for the new third-party request

**Observed:** `privacy.html` says the authored site is static HTML/CSS/local artwork and that no scripts are present. The latest commit adds JavaScript that calls `api.github.com` on the download page. The README similarly says no script/build process is needed, which is no longer precise.

**Update:** Describe the download page's optional browser-side request to GitHub's release API, its purpose, and the fallback behavior. Preserve the existing scope limitation that production hosting, logs, cookies and provider behavior have not been inspected. Correct README wording to say the site has no build step/dependency and uses a small optional release-refresh script; clarify that the script is not required for the checked-in links to work.

**Acceptance:** Privacy copy accurately enumerates authored external requests without making unverified host/data-retention guarantees. README statements about JavaScript and fallback operation match the implementation.

### P2 — Improve release-page user experience and resilience

**Observed:** The release-page link selector in the script targets only `a[href*="/releases/tag/"]`; the introductory link is currently updated only through generic version-string substitution, while links to the releases index intentionally remain static. If a platform asset is missing, a download button is hidden without an adjacent explanation. The API request can be delayed indefinitely.

**Update:** Use explicit, stable selectors/data attributes for the release version, release page links, asset links and checksum rows rather than relying on URL substring/suffix discovery across arbitrary anchors. Provide a concise status or availability explanation when refresh succeeds but an expected artifact is absent. Preserve static direct links when API data is unavailable. Ensure delayed refresh does not impair navigation or downloads.

**Acceptance:** The page stays useful before, during, and after refresh; supported links reliably point to the corresponding asset and release page; absent platform artifacts are not silently represented as available; API failure leaves checked-in links and checksums intact.

### P2 — Extend automated integrity checks for release data and site claims

**Observed:** `tools/check_site.py` checks local URLs and basic metadata/landmarks/CSS but does not validate the dynamic release page's required elements, fallback version consistency, checksum row structure, script inclusion, or privacy wording. Compiler diagnostics are not applicable to this static website, and no check was run in this plan-only review.

**Update:** Extend the dependency-free checker (or add focused tests appropriate to this framework-free project) to validate release-page fallback structure, one valid checksum pair per expected artifact, local script path, and consistency between checked-in release metadata/asset URLs. Add a controlled test strategy for the JavaScript updater using mocked DOM/fetch inputs if it can be done without adding production dependencies; otherwise document manual browser checks.

**Acceptance:** The integrity check catches malformed fallback markup, version/asset drift, missing script references and relevant local links. Validation covers API success, fallback failure path, missing asset and missing digest cases.

### P3 — Refresh launch readiness records only after owner verification

**Observed:** The evidence ledger and content plan still contain unresolved gates for product integration maturity, GitHub community/license state, content/artwork permissions, privacy contact/hosting behavior, and deployment settings. The deploy guide correctly marks these as conditional/unverified.

**Update:** Keep these items explicitly open; ask the owner to confirm current product maturity and approved wording, verify the actual latest release assets/checksums, confirm external GitHub channels/rights/privacy contact, and inspect current production hosting and DNS/HTTPS/404 configuration before changing public claims. Update evidence records with dates and scope after checks are actually performed. Do not alter `sitemap.xml` unless URLs change; no URL change is currently proposed.

**Acceptance:** Every closed launch gate has dated evidence and a clear scope. No new readiness, licensing, privacy, community, deployment, or per-platform runtime claim is published without confirmation.
